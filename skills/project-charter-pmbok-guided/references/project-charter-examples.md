# Project Charter Examples

These examples demonstrate how to apply the PMBOK-aligned Project Charter structure across different project types. They are illustrative examples; actual charters should be tailored based on project size, complexity, governance, organizational standards, and available information.

---

# Example 1: Enterprise Cloud Migration

## 1. Project Overview

| Field             | Value                             |
| ----------------- | --------------------------------- |
| Project Name      | Enterprise Cloud Migration        |
| Project Sponsor   | VP, Technology                    |
| Project Manager   | Senior Technical Project Manager  |
| Business Owner    | Director, Infrastructure Services |
| Target Completion | Q4 2027                           |
| Status            | Proposed                          |

## 2. Purpose, Business Need, and Expected Value

The organization currently operates several business-critical applications on aging on-premises infrastructure. Increasing infrastructure costs, limited scalability, hardware lifecycle risks, and disaster-recovery requirements have created a need to modernize the hosting environment.

The Enterprise Cloud Migration project will migrate prioritized applications and supporting infrastructure to an approved cloud platform.

Expected value includes improved scalability, infrastructure resilience, operational efficiency, security capabilities, and reduced dependency on aging data-center infrastructure.

## 3. Objectives and Success Criteria

### Objectives

* Migrate prioritized applications to the approved cloud environment by Q4 2027.
* Establish standardized cloud infrastructure and security controls.
* Minimize business disruption during application migration.
* Establish operational ownership and support processes before project closure.

### Success Criteria

The project will be considered successful when:

* 100% of applications approved for the project scope have been migrated or formally dispositioned.
* Migrated applications satisfy agreed functional and performance acceptance criteria.
* Required security and compliance controls have been validated.
* Production support ownership has been established.
* No unresolved Severity 1 migration-related defects remain at project closure.

## 4. Scope and Boundaries

### In Scope

* Assessment of identified applications
* Cloud infrastructure configuration
* Application migration
* Data migration where required
* Security and compliance validation
* Application testing
* Production cutover
* Operational transition
* Decommissioning planning for replaced infrastructure

### Out of Scope

* Major application redesign unrelated to migration requirements
* Replacement of business applications
* Migration of systems not included in the approved application inventory
* Broader enterprise data-center transformation initiatives

## 5. Major Deliverables and Requirements

Major deliverables include:

* Application migration assessment
* Approved cloud architecture
* Configured cloud environments
* Migration plans and runbooks
* Security and compliance validation
* Migrated applications
* Operational documentation
* Support transition plan
* Decommissioning recommendations

High-level requirements include:

* Compliance with organizational security standards
* Encryption of protected data in transit and at rest
* Defined rollback capability for production migrations
* Business-owner acceptance before production cutover

## 6. Milestones and Target Dates

| Milestone                       | Target  |
| ------------------------------- | ------- |
| Project Charter Approval        | Q1 2027 |
| Application Assessment Complete | Q1 2027 |
| Cloud Foundation Ready          | Q2 2027 |
| Migration Wave 1                | Q2 2027 |
| Migration Wave 2                | Q3 2027 |
| Final Migration Wave            | Q4 2027 |
| Operational Transition          | Q4 2027 |
| Project Closure                 | Q4 2027 |

## 7. Governance, Stakeholders, and Authority

The Project Sponsor provides executive direction, resolves escalated organizational issues, and approves material changes to project objectives, funding, and scope.

The Project Manager is authorized to:

* Coordinate cross-functional project activities.
* Develop and maintain the integrated project plan.
* Facilitate project decisions.
* Track risks, issues, dependencies, and milestones.
* Coordinate migration activities across participating teams.
* Escalate decisions outside delegated project authority.

Key stakeholders include:

* Technology leadership
* Application owners
* Infrastructure engineering
* Cloud engineering
* Cybersecurity
* Compliance
* Operations
* Business representatives

## 8. Assumptions, Constraints, Risks, and Dependencies

### Assumptions

* Application owners will provide appropriate SMEs.
* Required cloud services will be available within the approved enterprise environment.
* Business teams will participate in acceptance testing.

### Constraints

* Production outages must remain within approved maintenance windows.
* Migration activities must comply with enterprise security requirements.
* Project execution is limited to approved staffing and funding.

### High-Level Risks

| Risk                                                   | Potential Impact                                       |
| ------------------------------------------------------ | ------------------------------------------------------ |
| Legacy applications may not be cloud compatible        | Additional remediation could increase schedule or cost |
| SME availability may be limited                        | Decisions and testing could be delayed                 |
| Application dependencies may be incomplete             | Migration failures or schedule delays could occur      |
| Security requirements may require architecture changes | Migration timelines could be affected                  |

### Dependencies

* Cloud platform readiness
* Network connectivity
* Security architecture approval
* Application-owner participation
* Change-management approvals

## 9. Budget and Resource Summary

Required resource groups include:

* Project management
* Cloud engineering
* Infrastructure engineering
* Application engineering
* Security
* Operations
* Business SMEs

| Project Sponsor | TBD  | Pending      | TBD  |
| Business Owner  | TBD  | Pending      | TBD  |

# Example 2: Customer Service Process Improvement

## 1. Project Overview

| Field             | Value                                |
| ----------------- | ------------------------------------ |
| Project Name      | Customer Service Process Improvement |
| Sponsor           | VP, Customer Operations              |
| Project Manager   | TBD                                  |
| Business Owner    | Director, Customer Service           |
| Target Completion | Q2 2027                              |

## 2. Purpose, Business Need, and Expected Value

Customer-service representatives currently rely on multiple systems and manual processes to resolve common customer requests. The fragmented process increases handling time, creates inconsistent customer experiences, and requires duplicate data entry.

The project will streamline selected customer-service workflows and introduce standardized processes and supporting automation.

Expected value includes reduced manual effort, faster customer-service resolution, improved process consistency, and improved visibility into service performance.

## 3. Objectives and Success Criteria

### Objectives

* Standardize the highest-volume customer-service workflows.
* Reduce manual steps within selected processes.
* Implement approved workflow automation.
* Establish baseline and post-implementation performance measurements.
* Train impacted customer-service employees before rollout.

### Success Criteria

* Approved workflows are implemented and operational.
* 95% of impacted employees complete required training before rollout.
* Priority manual process steps identified for elimination are automated.
* Service-performance metrics are available after implementation.
* No unresolved critical operational issues remain at project closure.

## 4. Scope and Boundaries

### In Scope

* Current-state process assessment
* Priority workflow redesign
* Workflow automation
* Process documentation
* User acceptance testing
* Employee training
* Operational transition

### Out of Scope

* Replacement of the organization's CRM platform
* Organizational restructuring
* Changes to customer-service compensation policies
* Processes outside the approved customer-service functions

## 5. Major Deliverables and Requirements

Major deliverables:

* Current-state assessment
* Future-state process design
* Automated workflows
* Updated operating procedures
* Training materials
* Performance dashboard
* Transition plan

High-level requirements:

* Solutions must integrate with the existing CRM environment.
* Customer information must continue to follow organizational privacy requirements.
* Changes must be validated by customer-service SMEs before production deployment.

## 6. Milestones and Target Dates

| Milestone                | Target  |
| ------------------------ | ------- |
| Charter Approval         | TBD     |
| Current-State Assessment | TBD     |
| Future-State Design      | TBD     |
| Automation Complete      | TBD     |
| User Acceptance Testing  | TBD     |
| Training Complete        | TBD     |
| Production Rollout       | Q2 2027 |

## 7. Governance, Stakeholders, and Authority

The Sponsor owns the business outcome and provides executive direction.

The Project Manager coordinates work across Customer Service, Technology, Operations, and Training and escalates material scope, schedule, resource, and business decisions.

Key stakeholders include:

* Customer Service
* Operations
* Technology
* Training
* Customer Experience
* Compliance

## 8. Assumptions, Constraints, Risks, and Dependencies

**Assumptions**

* Customer-service SMEs will participate in process-design workshops.
* Existing technology can support the targeted automation.

**Constraints**

* Implementation must minimize disruption to daily customer-service operations.
* Training must be completed before rollout.

**Risks**

* Employee resistance could reduce adoption.
* Integration limitations could reduce automation opportunities.
* Limited SME availability could delay process validation.

**Dependencies**

* Customer-service SME availability
* Training-team availability

# Example 3: Generative AI Assistant Implementation

## 1. Project Overview

| Field             | Value                              |
| ----------------- | ---------------------------------- |
| Project Name      | Enterprise Generative AI Assistant |
| Sponsor           | Chief Technology Officer           |
| Project Manager   | Senior Technical Project Manager   |
| Business Owner    | Director, Digital Workplace        |
| Delivery Approach | Agile / Hybrid                     |
| Target Pilot      | Q3 2027                            |

## 2. Purpose, Business Need, and Expected Value

Employees spend significant time searching for organizational information, summarizing documents, preparing routine communications, and performing repetitive knowledge-work activities.

The project will pilot an enterprise Generative AI assistant to determine whether AI-assisted workflows can improve employee productivity while meeting organizational requirements for security, privacy, responsible AI, and data governance.

Expected value includes reduced time spent on repetitive knowledge work, improved access to organizational information, and increased organizational understanding of responsible enterprise AI adoption.

## 3. Objectives and Success Criteria

### Objectives

* Launch an enterprise AI-assistant pilot by Q3 2027.
* Enable a defined set of approved employee use cases.
* Establish security, privacy, and responsible-AI controls before pilot launch.
* Measure adoption, user satisfaction, and productivity indicators during the pilot.
* Produce recommendations for broader enterprise adoption.

### Success Criteria

* Pilot launches to the approved user population.
* 100% of approved use cases complete security and privacy review.
* No unresolved critical security findings exist at launch.
* Adoption and satisfaction metrics are captured throughout the pilot.
* Pilot findings and recommendations are presented to executive stakeholders.

## 4. Scope and Boundaries

### In Scope

* Enterprise AI assistant pilot
* Approved knowledge-worker use cases
* Identity and access integration
* Approved enterprise-data integration
* Security and privacy assessment
* Responsible-AI review
* Pilot-user training
* Adoption measurement
* Pilot evaluation

### Out of Scope

* Fully autonomous business decisions
* AI access to unapproved sensitive-data sources
* Enterprise-wide deployment before pilot evaluation
* Replacement of existing core business applications

## 5. Major Deliverables and Requirements

Major deliverables:

* Prioritized AI use cases
* Pilot architecture
* Security and privacy assessment
* Responsible-AI assessment
* Configured pilot environment
* User training and adoption plan
* Measurement framework
* Pilot findings and recommendations

High-level requirements:

* Authentication must use approved enterprise identity services.
* AI access must respect existing information-access permissions.
* Sensitive organizational information must be handled according to approved data policies.
* AI-generated information must not be represented as authoritative without appropriate validation for high-impact use cases.
* Usage and adoption metrics must be available for pilot evaluation.

## 6. Milestones and Target Dates

| Milestone                            | Target  |
| ------------------------------------ | ------- |
| Charter Approval                     | Q1 2027 |
| Use-Case Prioritization              | Q1 2027 |
| Architecture and Governance Approval | Q2 2027 |
| Pilot Environment Ready              | Q2 2027 |
| Pilot Launch                         | Q3 2027 |
| Pilot Evaluation                     | Q4 2027 |
| Executive Recommendation             | Q4 2027 |

## 7. Governance, Stakeholders, and Authority

Executive sponsorship is provided by the CTO.

A cross-functional governance group will provide oversight for security, privacy, responsible AI, legal, technology, and business considerations.

The Project Manager is authorized to coordinate project execution, facilitate cross-functional decisions, maintain the integrated delivery plan, track project risks and dependencies, and escalate decisions outside delegated authority.

Key stakeholders include:

* Digital Workplace
* Information Security
* Privacy
* Legal
* Responsible AI / AI Governance
* Enterprise Architecture
* IT Operations
* Business representatives
* Pilot users

## 8. Assumptions, Constraints, Risks, and Dependencies

### Assumptions

* Approved AI technology will be available for the pilot.
* Business groups will nominate pilot users.
* Required organizational data sources can be integrated subject to governance approval.

### Constraints

* Only approved enterprise data may be used.
* Security and privacy approval is required before pilot launch.
* Initial deployment is limited to the approved pilot population.

### Risks

| Risk                                           | Potential Impact                                     |
| ---------------------------------------------- | ---------------------------------------------------- |
| AI-generated inaccurate information            | Could reduce trust or create business risk           |
| Unauthorized exposure of sensitive information | Could create security, privacy, or compliance impact |
| Low user adoption                              | Could prevent meaningful pilot evaluation            |
| Unclear use cases                              | Could reduce measurable business value               |
| Rapid technology changes                       | Could require architecture or scope adjustments      |

### Dependencies

* Privacy approval

# Patterns Demonstrated by These Examples

The examples intentionally demonstrate several behaviors the Project Charter skill should reproduce:

1. **Tailor rather than mechanically populate every section.**
2. **Keep information at authorization level rather than creating a detailed project plan.**
3. **Connect business need → objectives → success criteria.**
4. **Clearly separate scope from out-of-scope items.**
5. **Separate assumptions, constraints, risks, and dependencies.**
6. **Describe project-manager authority without implying unlimited authority.**
7. **Use measurable success criteria when supporting information exists.**
8. **Use `TBD` rather than inventing missing information.**
9. **Identify unresolved decisions that need sponsor or stakeholder attention.**
10. **Adapt governance and requirements to the nature and risk of the project.**

# Anti-Pattern Example

Avoid generating a charter like this:

## Project Objective

Implement the new system successfully.

## Scope

Everything required to deliver the new system.

## Timeline

The project will take six months.

## Budget

$1,000,000.

## Risks

There may be delays.

## Success

The project will be successful when stakeholders are satisfied.

This is problematic because it contains vague objectives, undefined scope, unsupported schedule and budget assumptions, non-measurable success criteria, and risks that provide little information for decision-making.
